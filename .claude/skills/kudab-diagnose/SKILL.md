# Диагностика kudab и выбор следующей работы

Скилл собран после разбора 30–31.08.2026, где половина найденного противоречила тому,
что записано в документации и задачах проекта. Он существует ради одного: **не строить
решения на утверждениях, которые никто не проверял**.

## Главное правило

**Ни одно утверждение не попадает в вывод, пока не подтверждено дважды из независимых
источников.** Если два источника расходятся — верен тот, что выше в иерархии ниже, а
расхождение само становится находкой и идёт в отчёт отдельной строкой.

Особенно это касается утверждений, которые звучат как общеизвестные. Именно они и
оказываются враньём: их однажды записали и с тех пор не перепроверяли.

## Иерархия источников правды

Сверху — то, чему верить; снизу — то, что нужно перепроверять всегда.

| Источник | Доверие | Чем проверять |
|---|---|---|
| Живой прод (`curl`, headless-браузер) | высшее | это и есть реальность |
| API Метрики и Вебмастера | высшее для чисел | см. `[[kudab-analytics-access]]` в памяти |
| Живая база (`docker exec kudab-db psql`) | высокое | но dev-база бывает восстановлена из старого дампа |
| Код в `main` | среднее | **код в main ≠ то, что на проде**, пины сабмодулей отдельно |
| `TASKS.md`, `docs/*.md`, `ROADMAP.md` | низкое | протухает молча, дат в записях нет |
| Комментарии в коде | низкое | описывают замысел, а не сегодняшнее поведение |
| Память об этом проекте | низкое | могла устареть с прошлой сессии |

## Порядок работы

### 1. Собрать состояние, ничего не утверждая

Пройти по всем слоям и записать факты без выводов:

- **Что на проде против того, что в `main`.** Пины сабмодулей в infra, дата последнего
  деплоя, отпечатки в HTML живых страниц.
- **Незакоммиченное и незапушенное** во всех сабмодулях.
- **Числа за период** из Метрики и Вебмастера: посетители по дням, показы, клики,
  позиции, источники, индексация.
- **Открытые задачи** из `TASKS.md` всех сервисов — как гипотезы, не как факты.

### 2. Перепроверить каждое утверждение

Для каждого пункта, который собирается стать основанием решения, найти **второе
независимое подтверждение**. Примеры пар:

- «функция работает» → есть в коде **и** отвечает на проде (`curl`, а не чтение кода)
- «страница индексируется» → `robots`-мета в исходнике **и** запрос в Вебмастере
- «событие аналитики отправляется» → вызов в коде **и** перехват в headless на живой странице
- «цель считается» → отправляется в код **и** заведена в кабинете (проверять через API целей)
- «данных нет» → пусто в API **и** пусто в базе
- «это выросло» → сравнение однородных периодов, а не минимума с максимумом

### 3. Отдельно проверить, что деградировало тихо

Самые дорогие находки — не сломанное громко, а сломанное молча. Обязательный список:

- эндпоинты, у которых есть запасной путь: проверить, не падает ли основной
  (`try/catch` вокруг `$fetch` — красный флаг, лезть внутрь)
- маршруты, куда шлёт код: существуют ли они вообще
- пути, закрытые в `robots.txt`: не закрыто ли то, без чего страница не рисуется
- анимации и переходы, меняющие геометрию: не ломают ли они попадание курсором
- `sitemap`: соответствует ли содержимое обещанию (выборкой, а не заголовком)
- расхождение «миграция применена» и «таблица существует»

### 4. Приоритизировать

Кандидат в работу оценивается по четырём осям, и **каждая должна опираться на число**:

1. **Спрос подтверждён данными.** Не «кажется полезным», а показы, запросы, клики.
2. **Цена.** Часы, число файлов, нужен ли API, нужна ли миграция.
3. **Что разблокирует.** Есть ли задачи, которые ждут этой.
4. **Обратимость.** Что будет, если откатить.

Выигрывает не самое крупное, а то, где отношение подтверждённого спроса к цене выше.
Если спрос не подтверждён числом — кандидат не выигрывает никогда, даже если идея нравится.

### 5. Вынести решение

В выводе на каждое утверждение — источник и способ проверки. Формулировка вида
«похоже, что» допустима только с явной пометкой, что это гипотеза, и с указанием, чем её
проверить.

## Ловушки, на которых уже попадались

Каждая — из реального разбора, не гипотетическая.

**Документ, который врёт.** `docs/SEO_CORE.md` утверждал «весь органический трафик из
Яндекса». Метрика: Google 69,5%, Яндекс 30,2%. Ошибка жила потому, что подключён был
только Вебмастер, и его цифры выглядели полными.

**Задача, которая протухла.** `TASKS.md` говорил «осталось вручную завести цели в
Метрике». Цели были заведены. Проверка кабинета через API заняла минуту, а вывод на
основе записи был бы неверным.

**Код есть, прод не знает.** Между `main` и продом может лежать месяц: автодеплой
отключён, выкат руками.

**Тихий запасной путь.** `/api/web/sitemap/events` месяцами отвечал 500 из-за
ambiguous-колонки после join. Фронт ловил исключение и брал обычную ленту — в sitemap
ехали прошедшие события. В коде рядом стоял комментарий «эндпоинт пока отвечает 500».

**Метрика в никуда.** `/api/metrics` отдаёт 404, маршрута нет вовсе, а код исправно шлёт
туда события через `useMetrics().track()`.

**Выброс, принятый за уровень.** 76 посетителей — субботний пик; будни той же недели — 28.
Сравнивать надо однородные периоды.

**Рост, собранный из крайностей.** «Выросли с 15 до 76» — это минимум одного дня и
максимум другого. Честно: среднее первой половины месяца против второй.

**`aria-hidden` не для краулера.** Скрытый текст внутри `h1` читается роботом наравне с
заголовком.

**Анимация, съедающая нажатие.** Появление меток через `circle-radius` от нуля: MapLibre
считает зону попадания по радиусу, и пока он ноль, метки для курсора не существует.

## Что не считается доказательством

- «в коде написано, что работает»
- «в задачах помечено сделанным»
- «раньше проверяли»
- один замер там, где есть суточная или недельная сезонность
- скриншот инструмента проверки Google как доказательство пустоты страницы — он
  обрывается по таймауту, смотреть надо в HTML
- разница между двумя днями при дневном шуме ±23%

## Полезные команды

```bash
# что на проде против main
git -C . ls-tree HEAD services/ | grep commit
git submodule status

# отпечаток живой страницы
curl -s https://kudab.ru/ | grep -oP '<h1[^>]*>.*?</h1>'

# аналитика (токен и адреса — в памяти kudab-analytics-access)

# живая база
docker exec kudab-db psql -U kudab kudab -tAc "select ..."

# поведение живой страницы в браузере
docker exec kudab-headless node -e '...playwright...'
```

## Границы

Скилл диагностирует и приоритизирует. Он **не** принимает продуктовых решений за
владельца: если выбор упирается во вкус, в деньги или в то, каким владелец хочет видеть
проект, — вопрос выносится ему с готовыми числами по каждому варианту, а не решается молча.
