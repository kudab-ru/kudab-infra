# Проверка источников событий

Собрано после разбора 25.10.2026. Кассир пять дней собирался впустую: ссылки на события находились,
а страницы не разбирались, и ни одна проверка этого не заметила. МТС Live и Qtickets читались на первую
страницу из нескольких. Всё это видно за полчаса, если смотреть в нужное место.

## Когда

- **Каждый понедельник** вместе с `make coverage`: шаг 1, 10 минут.
- **Раз в месяц** или когда замер охвата просел: шаги 1–3, около часа.
- **Сразу**, если пришло оповещение о молчащем источнике или с какого-то сайта давно нет новых событий.

## Шаг 1. Живы ли прогоны

Главное — журнал прогонов `source_runs` на проде. SSH есть только у владельца: попросить его выполнить
запрос на сервере (`docker exec kudab-db psql -U kudab kudab -c "…"`) или работать из сессии на сервере.

```sql
select source_slug, count(*) runs, sum(posts_ok) ok, sum(posts_failed) failed,
       max(urls_total) urls, max(finished_at) last
from source_runs where started_at > now() - interval '7 days'
group by 1 order by 1;
```

Тревога:

- **`ok = 0` при `failed > 0`** — ссылки находятся, страницы не разбираются: сайт сменил разметку. Так сломался Кассир.
- **`urls = 0`** — не находятся ссылки: сменились список или адреса событий.
- **нет прогонов за сутки** у источника, который обходится раз в 3 часа: задание не ставится или у очереди
  `sites` нет обработчика (`php artisan horizon:supervisors` в контейнере Horizon должен показать `sites`).
- в журнале парсера (`storage/logs/laravel-*.log`) часто `site-source:rate-limited` (сайт отвечает 429) или
  `site-source:out-of-time` (обход не уложился в 420 с и сохранил часть).

`ok = 0` у llm_text-источника (квизы, театры с афишей текстом) — норма: все страницы уже собраны.

## Шаг 2. Читаем ли сайт целиком

Для больших источников (Кассир, МТС Live, Qtickets, QuickTickets, Культура.РФ, Я.Афиша):

- сколько ссылок на событиях на всех страницах списка против `urls_total` прогона и `listing_limit` профиля;
- есть ли у списка страницы дальше первой: `?page=2`, разделы, страницы дней;
- регэксп событий берёт все разделы сайта (у Кассира не брал `/shou/`, стендап и шоу шли мимо);
- у llm_text лимит считается после отсева собранного, а у jsonld за прогон читаются новые первыми — хвост
  длинного списка дочитывается за несколько прогонов, это нормально.

Сверка с продом: события источника (название, день) против `/api/web/events?city=voronezh&per_page=50&page=N`
(curl, Метрику не трогает). Совпадение — тот же день ±1 и общее значимое слово названия. Сверка завышает
пропуски примерно на четверть («NЮ» разбивается на латиницу и кириллицу), спорные проверять по точному названию.

## Шаг 3. Разметка страницы события

Две-три свежие страницы события обычным запросом, без браузера:

- есть ли `application/ld+json` с `"@type":"Event"` — тогда хватит профиля `jsonld`;
- нет — есть ли данные страницы для её скрипта: `__NUXT_DATA__` (Nuxt), `__NEXT_DATA__` (Next), Apollo-state.
  Из них событие собирается без браузера, как у Кассира и МТС (`app/Services/Sources/PageState/`);
- время: какой пояс и совпадает ли с тем, что видно на странице. Дважды попадались часы с неверной меткой.

## Как не навредить проверкой

- **Свои запросы съедают лимит сайта.** Кассир после ~50 страниц-списков за 20 минут стал отвечать 429 на
  все списки и держал запрет больше 40 минут; главную и страницы событий отдавал. Проверять на страницах
  событий, списки — по одному-два с паузой.
- **Стенд не копия прода**: другие id, стенд не собирает ВК, Telegram и Яндекс по расписанию. Выровнять —
  `make stand-pull-prod`. Числа охвата брать с прода.
- Контейнеры стенда не достают до `*.qtickets.events`, хост достаёт: Qtickets проверять с хоста
  (`env DB_HOST=127.0.0.1 REDIS_HOST=127.0.0.1 HOME=/tmp php artisan …`, `CACHE_STORE=array`).
- Не запускать общий `parser:events:extract` ради проверки: он отдаст модели чужие посты стенда. Свои посты
  разбирать `QticketsExtractJob::dispatchSync($id)`.
- Сбор одного источника на стенде — тем же заданием, что на проде:
  `app()->call([new FetchCommunityPostsFromApiJob($communityId, 3, $slug, $linkId, 10), 'handle'])` в tinker.

## Особенности источников

**Кассир** (`kassirvrn`). Разметки Event на странице нет с ~20.10, событие в `__NUXT_DATA__` →
`pinia['event.store'].eventState`. У спектакля с сеансами `eventState` пуст, сеансы — список
`eventListState`, берётся первый. Верное время только в `dateRangeWithTimezone`; `beginsAt` — московское
время с меткой UTC. Списки (`/category/*`, `/bilety-*`, `/detskaya-afisha`) ограничены, поэтому за прогон
8 указателей по кругу из 45. `/drugoe/`, `/doma-kultury/`, `/koncertnye-zaly/` — площадки, `/selection/` —
подборки, не события. Цены у Кассира читает и `KassirAdapter` (поиск цены по ссылке).

**МТС Live** (`live-mts-*`, по подборке на сообщество). Разметку Event дорисовывает скрипт, сервер отдаёт
`__NEXT_DATA__` → `initialState.Announcements.announcementDetails`. Время UTC без пояса (16:00 = 19:00),
а у рекомендаций на той же странице — местное. По 24 события на странице `?page=N`. В данных только
ближайший и последний сеанс, средних нет.

**Qtickets** (`qtickets`). Первая страница афиши — только ближайшие дни, вся афиша — на `?page=N`
(в октябре 16 страниц). Всю афишу читаем раз в три часа (метка `qtickets:full-listing:<город>` в кэше).
Страницы событий без браузера, точка карты — в `fn([широта, долгота])`.

**QuickTickets** (`quicktickets-*`). Касса перечисляет сеансы по спектаклям, не по датам: при малом лимите
теряется хвост. Возраст только в `<h1>…class="ageRestriction"`.

**Культура.РФ** (`culture-ru-voronezh`). Свой сборщик `CultureRuCollector`, `__NEXT_DATA__`, 45 страниц.
Страница без чужих просмотров отвечает ~5 с; `source_runs` не пишет — иначе самолечение переучит профиль.

**Я.Афиша**. Разделы по дням `?date=…&period=1` без браузера, не чаще раза в 4 часа. Если с сервера пошли
`headless:plain-no-marker` — антибот режет обычные запросы.

**llm_text-сайты** (театр оперы и балета, «Безантракта», квизы, «Тайная улица», Афиша.ру): каждая новая
страница — вызов модели, собранные не перечитываются (кроме афиш, перечитываемых ночью).

## Что делать при поломке

1. Шаг 3 — понять, что сменилось: адреса, список или разметка страницы.
2. Нет разметки, но есть данные страницы — новый класс в `PageState`, настройка `page_state` профиля.
3. Сменились адреса — `event_url_regex` или `index_url_regex` профиля. Самолечение
   (`parser:sources:self-heal`) переучивает только регэксп и только у jsonld, поломку разметки оно не чинит.
4. Настройки профиля на проде менять разовой задачей (образец — `ReadKassirAndMtsFromPageState`), и профиль
   задавать целиком: пока источник был сломан, самолечение могло переписать его регэксп.
5. Проверить сбором на стенде, потом разобрать свои посты и посмотреть события: время, площадка, цена.
