# Управление рассылкой из админки

План работ. Составлен 2026-09-08 после разведки по коду и живой базе.
Макеты: https://claude.ai/code/artifact/6ac75590-aa8c-449f-a5d3-6f4f606505c8

## Что хотим

Вести телеграм-рассылку из админки, а не из бота: лента на неделю вперёд,
которую сервис собирает сам и подсказывает варианты; закрепление постов,
правка текста, перенос даты. Панели управления в боте отключить.

**«Закрепить» = не заменять при пересборке недели.** Решено 2026-09-08.
Не «повторить пост»: повтор потребовал бы снять `UNIQUE(broadcast_id, event_id)`
и пересобрать все три анти-дубля, это отдельная и заметно большая работа.

## Что выяснила разведка

Пять вещей, из-за которых это не работа по интерфейсу. Всё проверено по коду
и запросами к живой базе, не выведено из общих соображений.

1. **Текста поста нигде нет.** API отдаёт боту только `event_id` и
   `template_code`, подпись собирает сам бот (`events.py:297-347`). Колонка
   `caption` в очереди заполняется только у портретов площадок — 7 строк из 99.
   Редактировать нечего, пока текст не начнут хранить.
2. **`planned_at` — не дата публикации,** а техническая придержка на шесть
   минут, пока генерится текст.
3. **«Одно событие в полёте»** (`TelegramChatBroadcastService.php:623-632`) —
   несущее допущение всей очереди. Именно из-за него одна отравленная запись
   остановила канал на 33 дня. Недельная лента его отменяет.
4. **Заполненная лента убьёт портреты площадок:**
   `TelegramVenuePortraitService.php:94` выходит при любой незакрытой записи
   канала. Если не развести счётчики, недельный каденс портретов молча умрёт.
5. **Наивный топ-7 даст неделю квестов одной сети.** 15 из топ-20 — Quest
   Brothers под четырьмя `venue_id`; события разные, группы разные, заголовки
   разные, поэтому ни один из трёх анти-дублей их не видит. Плюс скоринг почти
   не различает кандидатов: 133 из 138 набирают ≥80 при потолке 120 — ранжировать
   семь постов по такому баллу бессмысленно.

Пул при этом достаточный: 138 кандидатов на неделю, 93 уникальных заголовка.
Упрёмся не в него, а в однообразие и в кап `SCORING_CANDIDATE_LIMIT = 100`,
который сейчас покрывает только ~4.5 дня вперёд.

## Порядок работ

Порядок не произвольный: каждый следующий этап опирается на предыдущий, и
после каждого система остаётся рабочей — это важно, потому что деплой ручной.

### 1. Хранение текста поста

Без этого нет ни правки, ни честного превью, ни «своего текста».

- Перенести сборку подписи события из бота в API. Сейчас она в
  `app/bot/router/handlers/events.py:297-347`, шаблоны читаются из
  `telegram.message_templates`.
- Хранить готовый текст в `chat_broadcast_items.caption` и для `kind=event`,
  а не только для `venue`.
- Добавить признак «текст правили руками» (например `caption_source`:
  `template` / `manual`), чтобы пересборка не затирала правку и чтобы в
  интерфейсе было видно, откуда текст.
- Боту в задаче отдавать готовый `caption`, как уже делается для портретов.
  Ветку с `template_code` оставить на переходный период.

**Проверка:** пост, собранный API, побайтово совпадает с тем, что бот
собирал раньше. Взять 10 реальных событий и сравнить.

**Риск:** это единственный этап, который меняет то, что уходит в канал.
Делать первым и деплоить отдельно от остального.

### 2. Снять «одно событие в полёте»

- `countForBroadcast > 0` → сравнение с лимитом ленты (настройка канала,
  по умолчанию 7).
- **Считать event- и venue-айтемы раздельно**, иначе портреты площадок
  перестанут ставиться навсегда (`TelegramVenuePortraitService.php:94`).
- Анти-дубль третьего слоя сейчас смотрит только на `status='posted'`. Если
  неделя кладётся семью `planned`-айтемами, они друг для друга невидимы —
  два одинаковых заголовка в одной неделе никто не остановит. Расширить на
  незакрытые статусы.
- Поднять `SCORING_CANDIDATE_LIMIT` или заменить кап по количеству на границу
  по времени (`start_time < now + 7 дней`).
- Ввести настоящую дату публикации: либо перепрофилировать `planned_at` с
  явным переносом придержки в другое поле, либо завести `publish_at`.
  **Решить до начала этапа** — от этого зависит вся сортировка ленты.
- Колонка `is_pinned` + учёт при пересборке: закреплённые не трогаем,
  остальные слоты пересобираем.

**Проверка:** `broadcast:enqueue-due` ставит семь постов; портрет площадки
встаёт в свою неделю; повторный запуск не плодит дубли; закреплённый пост
переживает пересборку.

### 3. Разнообразие ленты

Иначе неделя будет из квестов, и первый же взгляд владельца на ленту это покажет.

- Свернуть сеть площадок: группировать кандидатов по владельцу/сети, а не
  только по `venue_id`. Ограничить долю одной сети в неделе.
- Отбор сделать итеративным с накоплением исключений — механика уже есть
  (`exclude_event_ids`), нужен цикл на семь шагов вместо одного.
- Отдавать наружу **причины**, а не балл: «темы ещё не было на неделе»,
  «площадку не показывали N недель», «скоро закончится», «бесплатное».
  Балл в интерфейсе не показывать — он не различает кандидатов.
- Снять вечное исключение: `rejected` и `skipped` сейчас в `usedStatuses`
  без окна давности, то есть однажды отклонённое событие выпадает из пула
  навсегда. При ручной правке ленты это накопится в невидимую эрозию.

**Проверка:** собрать неделю на живых данных и посмотреть глазами
распределение по темам и сетям. Считать долю самой частой сети.

### 4. Админское API

- Новая группа `/api/admin/broadcast/*` под тем же `auth:sanctum` +
  `role:admin|superadmin`, что и остальная админка. Существующие
  `/api/bot/broadcast/*` не трогать: у них своя авторизация общим токеном
  бота и права по `telegram_id`, админке через них ходить нельзя.
- Действия: список каналов, лента недели, пул предложений с причинами,
  поставить/убрать, закрепить/открепить, править текст, перенести дату,
  пересобрать неделю, настройки канала.
- Тесты рядом с существующими (`tests/Feature/Telegram`), запускать
  только через `make test-filter`.

### 5. Раздел в админке

Четыре экрана по макетам. Админка — Nuxt 4 + Tailwind без UI-библиотек,
свой мини-кит из пяти компонентов; готовых textarea, date-picker, DnD и
тостов в проекте **нет ни одного** — что понадобится, придётся написать.

- `app/pages/broadcast/index.vue` — лента недели.
- Пул предложений, карточка правки, настройки канала.
- Пункт в `nav` в `layouts/default.vue`.
- Образец списка с фильтрами — `pages/events/index.vue`; образец инлайн-правки
  с `notice` — `pages/venues/index.vue`; самый близкий сложный экран —
  `pages/sources/profiles.vue`.

### 6. Отключение панелей в боте

Последним, когда админка уже работает.

**Обязано остаться, иначе сломается тихо:**
- `kudab-bot-cron` — доставка (токен есть только у бота);
- `my_chat_member` (`channels.py:26`, `chat_members.py:18`) — без него новые
  каналы перестанут появляться в `telegram.chats`;
- ЛС-сигнал о простое (`type=notice`).

**Обязано уйти:** кнопка `bcst:send` «отправить сейчас» — публикует мимо
очереди и без claim-токена (`broadcast.py:269-283`). На недельной ленте это
готовый источник дублей.

**Осторожно:** если убрать обработчик `rev:*`, не отключив review-поток в API,
ЛС-превью продолжат уходить с мёртвыми кнопками, а айтемы будут висеть до
`broadcast:approve-timeouts` и уходить в канал как `auto_approved`.

## Чего в плане нет

- Повтор поста («закрепить» как переиздание) — см. решение выше.
- Редактор шаблонов сообщений в админке. `telegram.message_templates` сейчас
  только читается; отдельная работа.
- Чистка `chat_broadcast_items`. За полгода 99 строк, команды ретеншена нет —
  пока не проблема.
- `kudab-publisher`. Мёртвая заготовка на 54 строки: нет ни в одном
  compose-файле, образ никогда не собирался, переменных в `.env` нет,
  последний коммит 2025-07-20. К рассылке отношения не имеет, при случае удалить.
